## 1. 定位

Bounce Lite 是一个放在桌面上的互动小世界，不是目的明确的电子游戏。它服务于玩家短暂的空闲时间：玩家可以把一小段注意力投射进来，观察里面发生的事，并轻微地介入。它不要求玩家持续投入，但在玩家投入时提供可以想象和互动的内容。它不是桌面宠物，也不是挂机窗口。

核心关系是 Toy Partner：玩家不是在"玩球"，而是在"和球玩"。

> 玩家创造一个意图，球和世界共同回应这个意图，最终发生的事情永远比玩家预想的多一点。
> 玩家参与，但不统治；球回应，但不服从；世界变化，但不随机。

V0.1.x 已经建立了对象关系：球不是玩家控制的工具，而是有自主运动过程、会回应玩家介入的对象。V0.2 不重新扩展核心玩法，而是在这层关系之上，让球和它所在的世界产生更多值得停留、观察和重新想象的瞬间。

## 2. 上层原则

### 2.1 不检测观看

系统不尝试、也不需要检测玩家是否在观看。没有输入只是一个输入层面的事实，不据此推断玩家在看、走开了或已经离开。任何机制都不以"玩家在不在场"作为触发条件，也不以此来解释球的行为。

### 2.2 挡板是意图和介入的中介

- 挡板首先是一个真实的物理表面（Surface），其次才是玩家表达意图的媒介。它不是遥控器。
- 玩家的互动意图和介入行为都经由挡板进入系统，与鼠标等外部设备解耦：系统识别的是挡板动作，而不是鼠标像素。
- 玩家可以希望球朝某个方向走、尝试帮它碰到某个目标、尝试改变它当前的状态。最终结果由玩家输入、球的状态、物理运动和环境因素共同决定。
- 接触位置对反弹方向的有限影响（E01）已经过用户实测，确认保留。它是真实接触产生的物理结果，不是把玩家意图直接写进运动结果。

### 2.3 球的 lifecycle 固定

- ACTIVE → DECAYING → RESTING → Wake 或 Continue → ACTIVE，这是球本身的一条线，保持固定。
- **Wake**：强烈地把球从 RESTING 推向 ACTIVE。
- **Continue**：同样是这一步，但推力较弱。
- 要设计的是这条线牵涉到的时间、空间和玩家互动关系，而不是改写这条线本身。
- 现行分工：Wake 由挡板动作直接触发；Continue 由球在停稳后自己发起，玩家的互动关系只决定它有没有资格发生。

### 2.4 表现行为，不解释内心

球可以停下、恢复、回应玩家、偶尔偏离预期、呈现不同的运动状态，但不直接告诉玩家它开心、害怕或想要什么。目标不是做一个"有性格的角色"，而是做一个"允许玩家把它理解成伙伴的对象"。玩家和球的关系由观察和互动自然形成，不由系统预先定义。

### 2.5 可以有目标，但不做成任务

玩家可以自己产生目标，比如想让球碰到能量块、避开某个区域、保持运动。这些目标本身没有问题，问题在于目标不能成为唯一的评价标准。系统里没有分数、Combo、失败状态或完成清单。能量块是一个会让玩家产生收集意图的对象，不是系统规定必须收集的东西。

### 2.6 不确定性来自有规则的世界

"能影响，但不能完全决定"是核心乐趣。结果和操作完全对应，就成了控制系统；结果完全随机，玩家就失去了参与的意义。随机只用来决定世界里何时、何处、出现多久；对象一旦出现，它自身的规则保持稳定、可以学习。接触点要不要引入随机，等 E01 的规律建立之后再看。

### 2.7 事件驱动

先问"希望玩家经历一次什么样的事件"，再反推需要什么机制。机制服务于事件，而不是反过来。一个好的事件大致是这样展开的：

> 我想让它发生 → 我试着影响它 → 结果出现了一些变化 → 这个结果又让我有了新的想法

## 3. 架构边界

Physics、Interaction、Behavior、Feedback 四部分各自负责一块，可以互相影响，但不能互相替代。

| 部分 | 负责 | 不做 |
| --- | --- | --- |
| Physics | 位置、速度、碰撞、支撑、真实运动 | 不理解玩家意图 |
| Interaction | 玩家介入、意图表达、Wake 请求、对 Vitality 的影响 | 不直接控制物理结果 |
| Behavior | 球自身的倾向、lifecycle 状态变化、自主行为（例如 Continue） | 不绕过 Physics 直接改运动 |
| Feedback | 声音、光效、动画、视觉 | 不改变运动 |

- 跨越这几部分只能通过显式请求。世界通过加速度采样和"提供活力"参与，由球的物理循环来应用；Wake 和 Continue 都是先由 Physics 提交运动结果，再发布状态变化。
- 现状：Behavior 这部分职责目前写在 Ball 内部（例如 `play_rhythm`），还没有独立的代码层。是否把它抽出来，等合入 main 时再决定。

## 4. 三类事件与 V0.2.0 内容

| 类别 | 含义 | V0.2.0 内容 |
| --- | --- | --- |
| 环境事件 | 世界本身参与球的运动 | 转子：真实的碰撞体，被撞后留下的余转会改变局部气流。能量块：球与它重叠时提供活力，但不拉动轨迹，也不触发启动。 |
| 对象事件 | 让球本身更值得关注 | Wake 和 Continue 在 lifecycle 中的区分与各自的表现 |
| 互动事件 | 玩家和球一起完成某件事 | E01 的有限接触影响；玩家通过挡板引导球去接近转子或能量块，结果由球、物理和世界共同决定 |

### 4.1 场地与空间

- 整个可见的窗口客户区（client area）都成为世界。据此重新确定墙、地面、挡板高度，以及事件的生成有效区。
- 拉开挡板与地面的距离：一方面减少异常碰撞，另一方面让挡板下方成为真正属于球自己的区域。原型中这段间隙只有 35 px，而球的直径是 32 px。
- 默认窗口改为 640×480：逻辑视口仍是 960×720，所有几何不变，只是按比例缩小显示，窗口仍可自由缩放。原来默认 960×720 在横向上占去了半个屏幕。
- 已实现（2026-09-11）：视口 960×720 整体为世界，挡板中心 y = 570，挡板底边到地面 141 px，事件生成有效区为 (72, 72)–(888, 465)。详见[原型记录](../exploration/v0.2-shared-world.md)。
- 水平方向是玩家的互动空间，竖直方向是球自身的活动空间。

### 4.2 世界对象

- 转子和能量块的出现时间、出现位置、停留时间都是随机的；一旦出现，它们自身的规则保持稳定。
- 只在事件生成有效区内生成。
- 原型中转子的尺寸、气流强度、能量块的补给量和冷却时间等数值，都是创作选择，不是正式规格。

### 4.3 Wake 与 Continue

| | Wake | Continue |
| --- | --- | --- |
| 推力 | 强 | 弱 |
| 谁发起 | 挡板动作直接触发 | 球停稳后自己发起 |
| 与玩家的关系 | 由玩家介入直接引起 | 需要一次有效的挡板动作来获得资格 |
| 视觉 | 明显、带残留圈（从原型的 resume 表现移过来） | 更接近球自身运动过程的反馈 |

- Continue 资格判定的目标是"识别一次有效的挡板动作"。
- RESTING 可以细分：一种是互动中的短暂停顿，之后可能接一次 Continue；另一种是更深的安静。两者靠 lifecycle 的时间以及与挡板介入的关系来区分，不靠"玩家已经离开"这种推断（见 2.1）。

## 5. 实施顺序与后续调整计划

各步骤下列出的是届时要一起确定的事项。

1. **UI 和场地几何**：已完成（2026-09-11），待实机体验。
   - 球采用方案 B（核心恒亮、光晕双通道），挡板与球共用中心色，击球时挡板变暗、表现能量传给球。
   - 整个客户区成为世界，挡板抬高，挡板下方留出属于球的区域；默认窗口 640×480。
2. **转子和能量块随机出现**：下一步。
   - **数量、尺寸和出现频率。** 世界面积约为原来的 2.5 倍，对象尺寸没变；一条"跟随球"的模拟输入两分钟都没碰到转子。
   - **停留时间。** 要和转子的记忆时长、实际撞击频率一起定，否则同向叠加、反向刹停的规则在一次出现期间碰不上。
   - **生成与离场。** 不能生成在球当前所在的位置；转子带着余转时不离场，等转速衰减下来或球不在附近时再离开，避免气流突然消失。
   - **挡板恢复活力的比例。** 原型是恢复缺失量的 30%，这个值是按能量块常驻调的。补能改为断续出现后要重新评估，避免能量块变成事实上必须收集的东西。
3. **Continue 输入判定与 Wake / Continue 表现。**
   - **有效挡板动作的具体判定。** 建议方向，尚未确认：判定要和球有关，比如一次真实的有效接触，或者球在空中、在一定范围内时朝球方向移动的挡板动作；在任意位置移动挡板都不算。
   - **Continue 时间窗口的起点和时长。** 原型用的是 15 秒，按鼠标输入频率设定。建议改为从最后一次挡板介入开始计时，作为 lifecycle 的时间参数来调。
   - **强弱在参数上要一致。** 起跳速度 Wake 350 / Continue 290 px/s，符合"Wake 强"；但恢复的活力是 Wake 0.15 / Continue 0.22，方向反了。
   - **视觉交换（已定）。** 明显、带残留圈的表现给 Wake；Continue 降为更接近球自身运动过程的反馈。
   - **起跳撞到挡板底面。** 挡板在正上方时，从地面起跳（Wake 约 235 px，Continue 约 162 px）仍会撞到底面。球的线固定，这属于空间关系问题，不通过改起跳来解决。
4. **完整试玩一次。**

## 6. 参数调整与待试玩

以下事项不绑定某一步，在实机体验中持续调整。

- **转子值得做变体开发。** 当前"同向叠加、反向刹停或反转、有上限"的规则值得保留并继续发展，属于待探索方向。
- **转子参数需要测试调整。**
  - 包括衰减速度（记忆时长）、转速上限、气流半径和强度。
  - 现状：转速每 3.6 秒左右减半，而实际撞击约 13–18 秒一次，叠加和反转几乎碰不上。记忆时长和气流强弱目前由同一个变量（转速）决定，想要"记得久、风不一直大"就得把两者拆开。
  - 正面撞击的特例（按球的水平方向强行给转动量）会让刹车规律难读，建议去掉。
- **转子的线条在缩小窗口下太细，之后考虑加粗。** 气流弧线和转子外圈目前都是 1.2 px；默认窗口缩到 640×480 后，实际显示约为 0.8 px。
- **挡板亮度和变暗时间需要测试调整。** 当前常态 #80A2A8、变暗 #36494C；变暗深度 = lerp(0.55, 1.0, 传递量 ÷ 0.2)，保持 0.08 s 后在 0.5 s 内恢复。
- **所有体验层面的判断**，包括伙伴感、停留意愿和声画效果，都要等用户试玩。机器验证不能替代这一步。
