## 1. Confirmed Strengths

**S1．Wake 确实没有隐藏物理控制。** Fact。
`scripts/ball/ball_controller.gd:259-262` 中 Strong Wake 只写 `velocity.y = -tuning.wake_launch_speed`，不触碰 `velocity.x`，不读 Paddle 速度。`scripts/paddle/paddle_controller.gd:102` 发出的是 `_pending_input_distance`（clamp 后目标位移的无符号累计标量）与位置，不是 `velocity`。测试从三个独立轴向锁死了这一点：`tests/test_wake_sampling.gd` 覆盖 30/60/120 Hz × 左右两侧，断言 `velocity == Vector2(0,-350)`；`tests/test_paddle_support.gd` 覆盖 12.5 / 25 / 100 px 三档过量输入，断言启动速度与输入量级无关，且 `velocity.x == 0`。这是基线中「启动运动属于球重新活起来的物理表现，而不是对 Paddle 水平速度的直接复制」被实现得最干净的一处。

**S2．三条表达通道（Core/Glow ← Vitality，Trail ← Velocity，Paddle Feedback ← Interaction）在视觉层确实分离。** Fact。
`ball_visuals.gd:72` 中 `trail_color()` 恒为 `glow_color(1.0)`，与当前 vitality 无关；trail 的 alpha 与 ghost 数量只读 `_speed_ratio()`（`:112, :185`）。`core_color()/glow_peak()` 只读 vitality（`:53-64`）。碰撞/弱交互/Wake 反馈全部只写 `deformation`（`:132-155`），不进入颜色。`tests/test_ball_visuals.gd` 有正面断言：「Velocity cannot change Glow intensity」「collision decoration cannot boost Glow」「Wake decoration cannot boost Glow」「weak interaction does not pulse Glow」。

**S3．Physics → Vitality 的计算顺序契约成立。** Fact。
`surface_response_model.gd:21-71` 是纯函数：输入碰撞前的 velocity/vitality，输出 `velocity_after` 与 `vitality_delta`，自身不持有状态。`ball_controller.gd:203-204` 先应用速度、再应用活力增量，因此「本次碰撞用碰撞前的活力」这一语义成立，`tests/test_ball_controller.gd`「Ground current response uses pre-collision full Vitality」直接断言了它。

**S4．Paddle 视觉反馈已正确收口到真实碰撞。** Fact。
`paddle_contact` 只在碰撞循环内发出（`ball_controller.gd:85-86`），且支撑分支在 `:190` 提前 return，不发出；`main.gd:42` 只把 `ball.paddle_contact` 连到 `paddle.play_collision_feedback`，弱交互与 Strong Wake 都没有连线到 Paddle。这与 `docs/v0.1.5-paddle-interaction.md` 收口段的要求一致。

**S5．Support 与 Activity 是两个真正独立的维度。** Fact。
`SupportKind` 是 BallController 的局部状态（`ball_controller.gd:18-19`），`ActivityState` 在 `ball_vitality_model.gd:9-13`。`_refresh_support()` 失去支撑只清空 support 与采样，不改 Vitality（`:340-353`）；`advance_air_motion()` 对「RESTING 但无支撑」的球照常施加重力（`:170-172`），`tests/test_paddle_support.gd`「unsupported zero-velocity resting still falls」断言了这条。

**S6．音频节流有事件语义，不是简单去重。** Fact。
`basic_audio_feedback.gd:105-124` 同时使用 per-event cooldown、全局 `BURST_GAP`，并允许主交互打断已发出的 Wall 声（`:111-114`）。`:87, :94` 的分支刻意用 `result.surface_kind` 而非 `effective_surface_kind`，避免无效 Paddle 接触伪装成墙声——这是一处有意识的语义区分。

## 3. Design Concerns

### D1．游戏目标化倾向：已经存在，而且是当前最直接的设计冲突

**Fact．** HUD 常驻两个计数器：`COMBO n` 与 `TIME mm:ss`（`main.tscn:123-140`）。Combo 在每次有效接球 +1，**在球触地时归零**（`endless_rules.gd:21-29`）。Timer 在 RESTING 时暂停、在 Strong Wake 时归零重开（`:32-42`）。

**Reliable inference．** Combo 归零绑定 Ground 接触，等于在 UI 层把「球自己落地」重新定义为「玩家失误」。基线原文是「不要求玩家完成外部目标，也不通过分数、任务或失败状态持续占据注意力」，并且把落地明确写成球自身衰减过程的一部分（「一方面发生速度变化和能量损失，另一方面也可能消耗 Vitality」）。一个会因落地清零的连击数，是分数与失败状态两者的最小形式。

**这里两份文档互相矛盾，不是实现跑偏。** `AGENTS.md` 写「UI 仅 Combo 与可独立移除的当前活跃时间」，`docs/project_overview.md` §5 写「失败体验应表达『这一次没有接住』」——两者都为 Combo 留了位置。实现忠实执行了仓库文档，与你现在给的设计基线冲突。

**我的判断（这是判断，不是事实）：** Combo 应当删除，Timer 可以保留。理由是两者的语义方向不同——Combo 计量「玩家连续成功的次数」，指向玩家表现；Timer 计量「球保持活跃的时长」，指向球的状态，且它在 RESTING 时暂停、Wake 时归零，读起来更像「这一段活跃持续了多久」的行为证据，而不是成绩。若担心 Timer 仍带成绩暗示，可保留数据、弱化呈现（去掉 `TIME` 字样与固定角位，或只在活跃时淡入）。`AGENTS.md` 已把 Timer 标为「可独立移除」，这一改动在现有授权范围内。

### D2．Vitality 作为桥梁，两端都被压成近似二值

**Fact．** 恢复端：`paddle_vitality_restore = 1.0`，`_vitality_delta_for` 对 PADDLE 返回 `missing_vitality * 1.0`（`surface_response_model.gd:109-111`），即一次有效接球从任意活力直接补满。`tests/test_ball_controller.gd` 用「valid Paddle hit restores max Vitality」显式锁定了这个行为——它是有意的契约，不是遗漏。衰减端：`ground_vitality_retention = 0.65`，等比衰减，`0.65^6 ≈ 0.075 ≤ rest_vitality_ratio 0.08`，约 6 次落地进入可休息区间；墙/顶 0.985，一百次墙碰才降到 0.22，实际可忽略。

**Reliable inference．** 于是 Vitality 的实际取值分布是：接球后长期停在 1.0，或者落地后走一条约 6 步的等比下降。中间状态存在，但只在「已经开始往下掉且玩家没有介入」这一小段窗口里。Glow 直接映射 Vitality（`ball_visuals.gd:62-64`），所以玩家看到的更接近「满亮 / 逐级变暗 / 休息」，而不是基线描述的「明确但非线性的桥梁」。基线说的非线性，在实现里体现为衰减方向的等比曲线；恢复方向是硬复位，没有非线性可言。

**Model speculation．** 硬复位还有一个副作用：接球的**时机**不重要，接到就是满格。基线希望玩家「偶尔用挡板回应它」，而满格复位实际上奖励的是「接住」这个二值事件本身，这和 Combo 的激励方向是同一个。若把 `paddle_vitality_restore` 降到 0.4–0.6，恢复变成部分恢复，玩家需要多次回应才能把球带回高活力，桥梁的「非线性」在两个方向上才成立。这是体验猜测，需实机验证。

### D3．玩家几乎不影响球的方向

**Fact．** `paddle_tangent_retention = 1.0`（切向速度完全保留，不受 Paddle 影响）；Paddle 的实际 `velocity` 在 V0.1.5 之后不再连接到球的任何路径；`paddle_impulse = 160` 是沿法线的固定量，与接触点、Paddle 速度、球速都无关（`surface_response_model.gd:53-54`）。Paddle 碰撞形状是矩形，有效接球要求 `normal.y < -0.5`，即只有顶面，法线恒为 (0,-1)。

**Reliable inference．** 合起来：玩家能决定「什么时候接到」和「球是否继续活着」，但**完全不能决定球接下来往哪去**。球的水平速度在整个接球过程中不变。基线写的是「玩家影响球但不完全控制球」，当前实现落在这条谱的极端一侧——不是「不完全控制」，而是「方向上零影响」。

**这未必是缺陷。** 基线同时强调「未知的是球随后会怎样运动」，零方向影响确实最大化了这种未知。但它和 README 里「输入直接……每次拨动都会影响接下来的运动」「观察不同移动方式带来的反弹」是冲突的——不同移动方式带来的反弹目前完全一样。至少 README 该改。如果想让玩家有一点方向影响又不变成控制，最小改动是让接触点相对 Paddle 中心的偏移轻微改变出射法线（经典做法），或给 `paddle_tangent_retention` 一个略小于 1 的值让球在接触时略微「粘」向 Paddle 运动方向。前者会引入瞄准感，可能正是基线不想要的；后者更弱。**这是需要你决定的方向，不是我建议直接实施的改动。**

### D4．唤醒门槛可能低到会被无意触发

**Fact．** `wake_interaction_distance = 12.5` px，`wake_sample_seconds = 0.05` s，`wake_horizontal_range = 200` px。竞技场内宽约 615 px，半宽约 307 px。

**Reliable inference．** 阈值等价于「在 50 ms 窗口内累计 12.5 px 的目标位移」≈ 250 px/s 的鼠标水平速度，且窗口过期后重新累计。这是一个相当低的速度门槛。触发范围覆盖球两侧各 200 px，即竞技场宽度的约三分之二。

**Model speculation．** 玩家把鼠标从屏幕一侧移到另一侧、或只是想看看球停在哪，很可能就越过门槛把球唤醒。基线的核心句是「玩家决定是否继续互动，世界决定接下来会发生什么」——如果唤醒可以被无意触发，前半句就被削弱了。这条必须实机验证，静态阅读无法定论；仓库自己的人工门也把「阈值与 50 ms 节奏」列为待判断项。

### D5．衰减是事件驱动的，不是时间驱动的

**Fact．** 全仓库中 Vitality 的写入点只有四处：`reset_active`、`set_vitality`（测试与 F1 面板）、`apply_delta`（碰撞）、`wake`。没有任何以 `delta` 为参数的活力衰减。

**Reliable inference．** 「看它如何衰减」在实现上等于「数它落了几次地」。一个被持续接住的球活力永远是 1.0；一个在高处长时间飞行、暂时没触地的球活力也完全不掉。基线说 Vitality「影响运动在碰撞和时间中的维持能力」——碰撞维度成立，时间维度不存在。

这未必要改。事件驱动的衰减更可读、更容易与视听反馈对齐。但它决定了「衰减」这件事的节奏完全由落地频率给出，而落地频率又由重力和 restitution 决定，所以玩家看到的衰减速度实际上是**物理参数的函数，而不是一个独立的设计旋钮**。如果将来想调「球多久会停下来」，只能通过改 restitution 或重力实现，而这两者会同时改变手感。这是一处结构性的耦合，值得记下来。

### D6．Paddle 的 Surface 身份是单向的

**Fact．** `paddle_controller.gd:98` 直接写 `position.x = lerpf(...)`，从不调用 `move_and_collide` / `move_and_slide`；`velocity` 只是被记录下来供自身使用。球与 Paddle 的碰撞解算只发生在球自己移动时（`ball_controller.gd:69`）。

**Reliable inference．** 因此「Paddle 是一个真实 Surface」只在球→Paddle 方向成立。Paddle 高速横扫时可以移动进球当前占据的位置；下一帧球从已嵌入状态调用 `move_and_collide`，Godot 的退避行为在这种起始重叠情况下不保证给出合理法线。表现可能是穿透、卡住或异常弹射。

**未复现。** 本轮无法运行，这是从代码路径推出的机制，不是观察到的 bug。`AGENTS.md` 已把「已知高速 Paddle sweep」列为未展开项，说明你们也意识到了。它排在 P1 之外是因为触发条件苛刻（需要鼠标快速甩动且恰好扫过球），但一旦触发，玩家看到的是玩具「坏了」，而基线的整个说服力建立在球的行为可信上。

### D7．RESTING 时 Glow 被状态覆盖，Vitality 通道有一处轻微泄漏

**Fact．** `ball_visuals.gd:49-50` 的 `_visual_vitality()` 在 RESTING 时返回 0.0，忽略真实活力（此时真实值最高可到 0.08）。`glow_peak()` 在 RESTING 时也直接返回常量 0.25（`:62-64`）。

**Reliable inference．** 所以 Glow 表达的严格说是「经 Activity 状态修正的 Vitality」，不是纯 Vitality。冻结契约「Ball Core / Glow 表达 Vitality；禁止合并为 activity 值」在这一处被轻微违反。数值影响极小（0.25 vs `lerpf(0.25,0.85,0.08)=0.298`），且很可能是为了保证休息时球仍然可见而有意为之。列出来只是因为它是 Activity 唯一一处进入 Vitality 通道的地方，将来若有人以「Glow 只读 Vitality」为前提重构，这里会是意外来源。

## 4. 逐条回答你的 Review Focus

**Activity / Support / Physics 是否真正分离？**
结构上分离（S5、S3）；行为上有两处泄漏：BallController 内联的 Paddle 支撑规则绕过了 SurfaceResponseModel，`recover_out_of_bounds` 直接写 Activity 状态（Issue P1-1）。另外 support 状态在三个地方被写入（`_refresh_support`、`resolve_surface_collision`、`_settle_ground_position`），没有单一入口。

**Wake 是否仍隐藏物理控制？**
否，这一点做到了，且有强测试覆盖（S1）。但门槛可能低到被无意触发，那是另一个问题（D4）。

**Paddle 是否同时保持 Surface 与 Interaction 身份？**
Interaction 身份完整。Surface 身份单向：球撞 Paddle 成立，Paddle 撞球不成立（D6）。另外无效 Paddle 接触被降级为 WALL，导致「没接好比接好弹得更有劲」（Issue P2-2）。

**Feedback 是否绑定正确事件？**
Paddle 闪动、Wake 音效、支撑静音都绑定正确（S4、S6）。一处不一致：无效 Paddle 接触在音频通道和球体形变通道被判为不同表面（Issue P2-1）。四个 signal 无监听者（Issue P3-1）。

**玩家是否影响球但不完全控制球？**
方向上零影响，接近「完全不控制」而非「不完全控制」（D3）。

**球是否保持自主运动？**
是。重力固定、不随 Vitality 变化（`test_ball_controller` 有断言），Wake 启动固定，玩家不能注入方向。这一条实现得很彻底。

**Vitality 是否真正成为桥梁？**
部分成立。衰减方向是连续非线性的；恢复方向是硬复位到满格，桥梁在这一侧退化为开关（D2）。

**是否存在游戏目标化倾向？**
存在，且是当前与基线冲突最明确的一处：Combo 因触地归零（D1）。

**是否保留行为证据而非行为解释？**
保留得不错。没有文字提示、没有教学、没有状态标签，球的所有状态都通过 Glow / Trail / 形变 / 声音表达。唯一的例外是 HUD 的两个计数器——它们是解释（「你连了几次」「你活跃了多久」），不是证据。删掉 Combo 后这一条基本干净。

## 5. Recommended Actions

按「改动量 / 需要你决定的程度」排序。**都不是我要求执行的方案，是审查结论对应的最小动作。**

**需要你先决定方向的（不动代码）**

1. **裁决 Combo 的去留。** 这是设计基线与 `AGENTS.md`／`project_overview.md` 之间的直接冲突，不能由实现层解决。我的意见是删 Combo、留 Timer 并弱化呈现（D1）。
2. **裁决玩家是否应有方向影响。** 当前是零影响，README 的描述与之不符。要么改 README，要么引入一点方向影响（D3）。两个选择都自洽，但必须选一个。
3. **实机验证唤醒门槛。** 12.5 px / 50 ms / 200 px 三个数是否会导致无意唤醒，只能试玩判断（D4）。

**结构性、建议排进下一轮（改动明确、范围有界）**

4. **把 Paddle 支撑规则移入 SurfaceResponseModel，或明确把它记为契约例外。** 现状是契约上说「唯一决策点」，实现上有三个决策点。两条路都可以，但不该让文档和代码继续互相矛盾（Issue P1-1）。
5. **给 Wake 采样顺序一个显式保证。** 设置 `process_priority`，或加一条场景级回归断言 Ball 先于 Paddle 处理。目前它靠 `main.tscn` 里两行的先后顺序（Issue P1-2）。
6. **统一几何来源。** 让 `safe_center_bounds()` 与 `_paddle_support_y()` 从碰撞形状读半径/尺寸，或至少把 `ball_radius` 从 `@export_group("Ball Visuals")` 移出并注释说明它同时是物理量（Issue P1-3）。

**低成本清理（可以顺手做）**

7. 让球体形变与音频对「无效 Paddle 接触」使用同一个 kind 判定（Issue P2-1）。
8. 删除或接线四个无监听者的 signal 与 public `interaction_strength`（Issue P3-1）。
9. 让 `main.gd` 只启动球一次，明确开局方向（Issue P3-2）。
10. HUD 只在文本变化时刷新（Issue P3-3）。

**验证缺口（下轮无论做不做上面的改动，都值得补）**

11. 现有测试全部绕过场景 tree order 与真实碰撞循环，直接手工调用方法。缺一条真正跑 `main.tscn` 若干帧、检查 Wake 采样顺序与 Paddle 高速横扫的场景回归。`docs/v0.1.5-paddle-interaction.md` 提到跑了 1200 帧主场景，但那是「不崩溃」级别的验证，不是行为断言。
