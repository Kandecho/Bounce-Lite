## 3. Bug

### B1 · 冻结的三通道原则与现有测试断言直接冲突

| 字段 | 值 |
| --- | --- |
| 分类 | Bug（规格 / 测试一致性） |
| 严重程度 | 高 |
| 影响范围 | Ball 视觉实现、`tests/test_ball_visuals.gd` |
| 是否阻塞 | **阻塞视觉实现**；不阻塞 V0.1.3 人工试玩 |
| 状态 | 待确认（依赖 DD1） |

`tests/test_ball_visuals.gd` 将「Interaction 事件改变 Ball Glow」固化为契约：

```gdscript
suite.expect_true(paddle_glow > 0.0, "Paddle hit boosts Glow")
suite.expect_true(visuals.glow_pulse < paddle_glow, "Wall feedback is weaker than Paddle feedback")
suite.expect_true(visuals.darken_pulse > 0.0, "Ground hit briefly darkens the Ball")
suite.expect_true(visuals.glow_pulse > paddle_glow, "Wake produces the strongest light pulse")
```

而 `visual_spec.md` §1.1（本次冻结）规定 Ball Glow 只表达 Vitality。严格按原则实现时，上述四条断言将全部失败。

同一文件另有一处量纲冲突：

```gdscript
suite.expect_equal(fast_trail_size, 16, "fast motion keeps the full light-trail history")
```

硬编码 `trail_max_samples = 16`，而冻结规格为离散残影 `n ≤ 4`（`visual_spec` §11.4）。

**推荐处理**：先裁决 `DD1`，再据结论修改断言。不得在实现过程中顺手调整这四条——它们是有意写入的契约，任何修改都应是被记录的决定。

### B3 · `configure()` 带副作用地重开一局

| 字段 | 值 |
| --- | --- |
| 分类 | Bug（职责边界；当前无可见错误行为） |
| 严重程度 | 低 |
| 影响范围 | `scripts/ball/ball_controller.gd` 生命周期 |
| 是否阻塞 | 否 |
| 状态 | 待确认 |

`BallController.configure()` 末尾调用 `start_active(DEFAULT_DIRECTION)`。实际启动路径执行三次初始化：

1. `Ball._ready()` → `configure(自带默认 tuning)` → `start_active((0.65, -1.0))`
2. `Main._ready()` → `ball.configure(共享 tuning)` → `start_active((0.65, -1.0))`
3. `Main._ready()` → `ball.start_active((0.62, 1.0))`

最终状态正确，因此当前没有可观察的错误。

问题在于 `configure()` 同时承担「装配依赖」与「开局」两个职责。任何将来在运行中调用 `configure()` 的路径——例如 F1 面板支持切换 tuning 实例、脚本热重载——都会静默重开一局。

**推荐处理**：将 `start_active()` 移出 `configure()`，由调用方显式开局。改动范围小，风险低。

| 分类 | Design Decision |

| 是否阻塞 | 阻塞视觉实现 |

`ball_visuals.gd` 中 `glow_pulse` 由 `play_collision_feedback()`（Paddle / Wall）与 `play_wake_feedback()` 设置，`darken_pulse` 由 Ground 设置；两者直接加入 `glow_strength` 与核心色计算。

两种读法都成立：

- **甲**：碰撞脉冲属于 Interaction 通道的输出，画在球上属于串道，应全部迁移到 Paddle（A035 / A036）；

冻结规格未裁决此项。它直接决定实现时是否保留球上的 `glow_pulse` / `darken_pulse`。**不判定为问题。**

## 6. 已核对、判定为非问题

登记这一节是因为「查过并排除」与「未查」的价值不同。

1. **旧 API 残留：0 命中。** 全仓库搜索 `BallEnergyModel`、`ball_energy_model`、`energy_model`、`activity_ratio`、`set_activity`、`wake_speed`、`wake_paddle_velocity`、`wake_hold_seconds`、`wake_vitality_ratio`、`handle_wake_gesture`、`wake_from_paddle`、`advance_wake_detector`、`configure_ball`，全部零引用。V0.1.2 与 V0.1.3 两轮重构的收尾干净。
2. **通道纯度自动化断言已存在。** 审查中原本准备登记「缺少通道互不串扰断言」，读取 `tests/test_ball_visuals.gd` 后撤回。已有五条：Trail 长度 / 容量 / 宽度独立于 Vitality、Glow 范围独立于 Velocity、低速时提高 Vitality 不延长 Trail。缺口仅在 Glow **强度** 对 Velocity 的独立性，而该条恰好卡在 `DD1` 上，现阶段不宜补。
3. **一次性冲量消费标记的复位路径。** `resting_wake_impulse_consumed` 仅在 Ground settle 时复位，理论上存在「无法二次唤醒」路径，但按当前参数不可达：低 Vitality 下 Ground restitution ≈ `0.12 + 0.66 × 0.07 = 0.166`，需落地速度 `> 271 px/s` 才会超过 `rest_settle_speed = 45`，而弱冲量（上限即激活阈值 180）产生不了该速度。F1 面板仅暴露 `ground_restitution_max`，在低 Vitality 下调高它的影响也不足（`0.166 → 0.18`）。
4. **F1 运行时调参面板映射一致。** 13 项参数与 `PrototypeTuning` 的 43 个属性对应正确；SpinBox 的 `min` / `max` 未超出对应 `@export_range`；`invert` 项（Vitality loss）的双向换算对称。
5. **HUD 每帧重建字符串。** `EndlessRules.advance_active_time()` 每帧发射 `active_time_changed`，`PrototypeHUD` 每次重新格式化并赋值 `Label.text`，约 60 次 / 秒的字符串分配。原型阶段可接受，不构成问题。
6. **`motion_sampled` 每物理帧发射。** 唯一消费者在非 RESTING 时立即早退，无性能影响。信号命名偏通用（实际契约是「唤醒输入候选」），但不构成缺陷。
