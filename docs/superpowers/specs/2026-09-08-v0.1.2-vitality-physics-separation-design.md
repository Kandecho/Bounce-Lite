# Bounce Lite V0.1.2 Vitality–Physics Separation 技术设计

状态：方案方向已确认，文档化细节待用户复核

日期：2026-09-08

阶段：V0.1.2 - Vitality–Physics Separation

基线提交：`18c1931 chore: snapshot v0.1.1 endless prototype baseline`

## 1. 目标

V0.1.2 将 V0.1.1 的 Energy-driven Motion 重构为两个边界清楚的领域：

```text
Physics State                 Vitality State
├── Position                  ├── Inflation / Elasticity
├── Velocity                  ├── Bounce capability
├── Gravity                   ├── Activity state
└── Collision                 └── Visual intensity
```

核心定义：

- Velocity 描述球现在如何运动；
- Vitality 描述球还能保持运动状态的能力；
- 两者相关，但不互相替代；
- Vitality 可以影响一次碰撞的恢复能力，但不能直接重建 Velocity；
- 本次是领域重划分，不是把 `Energy` 字段机械改名为 `Vitality`。

## 2. 本版本范围

本次验证：

1. Velocity 与 Vitality 是否能够独立演化；
2. 球是否自然经历“运动 → 碰撞损耗 → 低弹性 → 休眠”；
3. Paddle 是否表现为玩家向系统重新输入运动的接口；
4. Trail 与 Glow 是否分别表达 Motion 与 Vitality。

本次不做：

- Combo 命名或规则重构；
- HUD 重构；
- Theme Token 或主题切换；
- 正式音效或 Audio 系统；
- Paddle 分区、技能或特殊击球；
- Classic、Recover 或其他玩法模式；
- 正式素材、复杂 Shader、粒子或视觉精修；
- 全局 Event Bus 或大型数据驱动 Surface 框架。

## 3. 依赖方向

```text
Paddle Input
    ↓
BallController collision detection
    ↓
SurfaceResponseModel.resolve(...)
    ↓
SurfaceCollisionResult
    ↓
BallController applies Velocity
    ↓
BallVitalityModel.apply_delta(...)
    ↓
BallVitalityModel resolves ActivityState
    ↓
local domain signals
    ↓
BallVisuals / EndlessRules
```

约束：

- 低层规则返回结果，不直接修改外部对象；
- BallController 是编排者，不拥有 Surface 或 Vitality 公式；
- BallVitalityModel 不知道 Wall、Ground、Paddle 等世界对象；
- BallVisuals 和 EndlessRules 不反向读取 BallController；
- 当前使用局部 signals 作为事件层，不增加全局单例。

## 4. 模块职责

### 4.1 BallController

负责：

- CharacterBody2D 的位置和 Velocity；
- 固定重力积分；
- `move_and_collide()` 碰撞检测；
- 从 collider metadata 取得 SurfaceKind；
- 调用 SurfaceResponseModel；
- 按固定顺序应用 CollisionResult；
- 把 Motion/Vitality 快照推送给 Visual；
- 在结算后发送局部领域事件。

不负责：

- Surface 的恢复系数、摩擦、Vitality 损耗或 Paddle impulse 公式；
- Vitality clamp、状态阈值或状态切换规则；
- Glow、Trail 或其他绘制规则；
- Combo、Timer 等 Endless 规则。

### 4.2 BallVitalityModel

`BallVitalityModel extends RefCounted`，不访问 Node、输入、碰撞或渲染 API。

维护：

```gdscript
current_vitality: float
max_vitality: float
state: ActivityState
```

保证：

```text
0 <= current_vitality <= max_vitality
```

提供的领域接口仅包括：

```gdscript
reset_active()
apply_delta(delta: float)
set_vitality(value: float)
resolve_activity(settle_allowed: bool)
wake(target_vitality: float)
vitality_ratio() -> float
```

它不持有：

- SurfaceKind；
- Wall/Top/Ground/Paddle 分支；
- restitution、friction 或 impulse；
- Velocity、speed mapping 或 direction。

SurfaceResponseModel 把 Surface 规则换算为 `vitality_delta`，BallVitalityModel 只负责应用、clamp 和状态结算。

### 4.3 SurfaceResponseModel

`SurfaceResponseModel extends RefCounted`，是确定性的纯计算服务。

输入：

```gdscript
resolve(
    velocity_before: Vector2,
    collision_normal: Vector2,
    surface_kind: SurfaceKind,
    vitality_ratio_before: float,
    vitality_before: float,
    max_vitality: float,
    valid_paddle_hit: bool
) -> SurfaceCollisionResult
```

输出但不应用：

- `velocity_after`；
- `vitality_delta`；
- `effective_surface_kind`；
- `settle_allowed`；
- `valid_paddle_hit`；
- 事件所需的碰撞前后快照。

禁止直接修改：

- BallController；
- BallVitalityModel；
- BallVisuals；
- EndlessRules。

当前 Surface 参数继续集中在 PrototypeTuning。V0.1.2 不为每种 Surface 创建 Resource；未来 Surface 类型显著增加时再评估数据驱动 profile。

### 4.4 SurfaceCollisionResult

CollisionResult 是一次结算的纯数据载体，至少包含：

```gdscript
surface_kind: int
effective_surface_kind: int
normal: Vector2
velocity_before: Vector2
velocity_after: Vector2
vitality_before: float
vitality_delta: float
vitality_after: float
valid_paddle_hit: bool
settle_allowed: bool
```

`vitality_after` 是便于断言、日志和事件消费的计算快照；实际状态仍由 BallVitalityModel 在 `apply_delta()` 后拥有。

Result 创建后按只读值对象使用，不允许下游修改后反向影响物理结算。

## 5. Surface 类型与场景兼容

SurfaceKind 从 BallEnergyModel 移到物理响应边界，保留现有数值顺序：

```gdscript
enum SurfaceKind {
    WALL = 0,
    TOP = 1,
    GROUND = 2,
    PADDLE = 3,
}
```

这样 `scenes/main.tscn` 现有 `metadata/surface_kind` 无需批量重写。

有效 Paddle hit 仍要求：

- 当前 SurfaceKind 为 PADDLE；
- Ball 向下运动；
- collision normal 指向上方并满足现有 top-face 条件。

无效的 Paddle 侧面或底面接触使用 Wall-like 响应，不增加 Combo、不施加 Paddle impulse、不恢复 Vitality。

## 6. 固定碰撞结算时序

每次碰撞严格采用：

```text
1. 保存 velocity_before 与 vitality_before
2. 用 velocity_before + vitality_before 计算 SurfaceCollisionResult
3. BallController 应用并限制 velocity_after
4. BallVitalityModel.apply_delta(vitality_delta)
5. BallVitalityModel.resolve_activity(settle_allowed)
6. 如果进入 RESTING，BallController 将 Velocity 归零
7. 发送 collision / vitality / activity events
8. Visual 与 Rules 消费事件或快照
```

禁止：

```text
先修改 Vitality
→ 再用修改后的 Vitality 计算当前碰撞
```

本次事件由碰撞发生前的状态决定；Vitality 变化只影响下一次运动和碰撞。

## 7. Surface Response 算法

### 7.1 通用法向/切向分解

对合法 normal：

```text
normal_component  = normal * velocity.dot(normal)
tangent_component = velocity - normal_component

velocity_after =
    tangent_component * tangent_retention
    - normal_component * restitution
```

其中 `restitution` 由 Surface profile 与碰撞前的 Vitality ratio 共同确定：

```text
restitution = lerp(min_restitution, max_restitution, vitality_ratio_before)
```

最后统一执行：

```text
velocity_after = velocity_after.limit_length(max_speed)
```

非法或零 normal 不进行反射；Result 保留输入 Velocity，并返回零 Vitality delta，避免制造非确定性方向。

### 7.2 Wall / Top

目标：改变方向、轻微速度损失、轻微 Vitality 磨损。

初始调试起点：

| 参数 | Wall | Top |
|---|---:|---:|
| min restitution | 0.96 | 0.96 |
| max restitution | 0.995 | 0.995 |
| tangent retention | 0.995 | 0.995 |
| vitality retention | 0.985 | 0.985 |

Vitality delta 按碰撞前值计算：

```text
vitality_delta = vitality_before * vitality_retention - vitality_before
```

因此环境碰撞始终满足 `vitality_after <= vitality_before`。

### 7.3 Ground

目标：形成强耗散、逐次降低反弹高度，并在低弹性阶段进入小跳/滚动。

初始调试起点：

| 参数 | 值 |
|---|---:|
| min restitution | 0.12 |
| max restitution | 0.78 |
| tangent retention | 0.80 |
| vitality retention | 0.65 |

第一次高 Vitality Ground collision 使用碰撞前高恢复系数完成本次反弹；随后才把 Vitality 降低到 65%。下一次 Ground collision 才使用降低后的恢复能力。

这保证：

- 当前状态决定当前事件；
- 高 Vitality 时仍有明显反弹；
- 后续反弹高度逐步降低；
- 切向速度通过 Ground friction 逐步衰减，而不是瞬间归零。

### 7.4 Paddle

Paddle 使用同一个通用碰撞算法，不建立独立物理系统。

有效 top-face hit 的结算顺序：

```text
通用法向/切向响应
→ 沿 collision normal 加固定 paddle_impulse
→ max_speed 限制
→ 生成恢复到 max_vitality 所需的 vitality_delta
```

初始调试起点：

| 参数 | 值 |
|---|---:|
| min restitution | 0.72 |
| max restitution | 0.92 |
| tangent retention | 1.00 |
| fixed paddle impulse | 160 px/s |
| vitality target | max_vitality |

恢复 delta：

```text
vitality_delta = max_vitality - vitality_before
```

固定 impulse 不读取 Paddle 速度；玩家只需接到球即可注入运动。连续成功仍受 `max_speed` 限制，不会无限加速。

接触位置改变方向是允许扩展点，但不是 V0.1.2 必做项；本次不加入 Paddle 分区或区域奖励。

## 8. Velocity 生命周期

Velocity 的来源只有：

```text
previous Velocity
+ fixed Gravity
+ Surface collision response
+ fixed Paddle impulse
```

保持：

- 初始启动速度约 `360 px/s`；
- 固定重力 `520 px/s²`；
- 最大速度 `520 px/s`；
- Wake 启动速度约 `330 px/s`。

删除：

- `speed_for_current_energy()`；
- `energy_for_speed()`；
- `_sync_velocity_from_energy()`；
- 任何由 Vitality 重新构造完整 Velocity 的路径。

Paddle 恢复 Vitality 后不会把正在运动的 Ball 强制改回某个“目标速度”；速度变化只来自本次碰撞响应与固定 impulse。

## 9. Vitality 与 ActivityState

ActivityState 保持：

```text
ACTIVE
DECAYING
RESTING
```

初始调试起点：

| 参数 | 值 |
|---|---:|
| max_vitality | 1.00 |
| active threshold ratio | 0.70 |
| rest threshold ratio | 0.08 |
| wake vitality ratio | 0.85 |
| settle speed threshold | 45 px/s |

状态规则：

```text
ACTIVE:
    vitality_ratio >= active_threshold

DECAYING:
    vitality_ratio < active_threshold
    且尚未满足休眠联合条件

RESTING:
    vitality_ratio <= rest_threshold
    且 settle_allowed == true
```

`settle_allowed` 由 SurfaceResponseModel 根据以下事实计算：

- 当前有效 Surface 为 Ground；
- `velocity_after.length()` 已低于 settle speed threshold。

BallVitalityModel 只收到布尔值，不知道它来自 Ground。这样可同时满足：

- VitalityModel 不依赖 Surface；
- Resting 由低 Vitality 和可安定的物理状态联合决定；
- Wall 损耗不会令球在空中突然冻结；
- Ball 会经过小幅跳动/滚动后再进入 RESTING。

若 Vitality 已低但尚未允许休眠，状态保持 DECAYING。

## 10. Wake

Wake 手势保持 V0.1.1 规则：

- RESTING 时检测 Paddle 有效水平移动；
- Paddle velocity 超过阈值并持续约 `80 ms`；
- latch 继续防止同一次手势重复触发。

Wake 明确拆成两个互不推导的值：

```text
wake launch velocity = direction * wake_speed
wake vitality        = max_vitality * wake_vitality_ratio
```

初始继续使用 `wake_speed = 330 px/s`、`wake_vitality_ratio = 0.85`。Wake 是非碰撞启动事件，不经过 SurfaceResponseModel。

## 11. Visual 数据边界

BallVisuals 不主动持有或查询 BallController/BallVitalityModel 引用，由 Controller 推送最小快照。

### Trail

Trail 只消费 Motion：

```gdscript
set_motion(velocity: Vector2)
record_ball_position(position: Vector2)
```

Trail 的：

- 长度；
- 采样容量；
- 透明度；
- 消散程度；

只由实际 Velocity 决定，不读取 vitality ratio。Velocity 归零后清空或快速消散。

### Glow

Glow 只消费 Vitality：

```gdscript
set_vitality(vitality_ratio: float, activity_state: int)
```

Glow 的亮度、范围和密度只表达 Vitality；RESTING 保留微弱存在感。

碰撞 squash/stretch、Ground darken、Paddle/Wake pulse 继续由离散事件触发，不改变 Trail 与 Glow 的基础语义。

## 12. Event 层

当前 Event 层使用局部 signals，不增加全局 bus：

- `surface_resolved(result)`；
- `paddle_hit(vitality_before, vitality_after)`；
- `surface_hit(kind, vitality_before, vitality_after)`；
- `vitality_changed(previous, current)`；
- `activity_state_changed(previous, current)`；
- 现有 EndlessRules 的 `rest_started` / `wake_started`。

发送时机统一在 Velocity、Vitality 和 ActivityState 全部结算完成之后。

Visual 通过推送的 Motion/Vitality 快照和离散碰撞事件更新；Rules 通过语义事件更新 Combo/Timer。后续 Audio 可以订阅相同事件，但 V0.1.2 不创建 Audio 节点或音频资产。

## 13. TDD 边界

必须覆盖的确定性规则：

### BallVitalityModel

- clamp 保证 `0 <= vitality <= max_vitality`；
- apply_delta 正负变化正确；
- Surface 名称不出现在模型 API；
- ACTIVE / DECAYING 阈值正确；
- 低 Vitality 但 `settle_allowed == false` 不进入 RESTING；
- 低 Vitality 且 `settle_allowed == true` 进入 RESTING；
- Wake 只对 RESTING 生效并恢复指定 Vitality。

### SurfaceResponseModel

- Wall/Top 改变法向方向且只产生轻微耗散；
- Ground 使用碰撞前 Vitality 计算本次恢复系数；
- Ground 的 Vitality delta 大于 Wall/Top 损耗；
- Paddle 先完成普通响应，再增加固定 impulse，再限制最大速度；
- Paddle impulse 不随 Paddle velocity 改变；
- 有效 Paddle hit 生成恢复到 max 的 delta；
- 无效 Paddle contact 使用 Wall-like 响应；
- 零 normal 不制造新方向或 Vitality 变化；
- settle_allowed 只在 Ground 且响应后速度足够低时成立。

### BallController 集成

- 固定重力继续独立于 Vitality；
- 修改 Vitality 不会立即改变当前 Velocity；
- 当前碰撞使用 vitality_before，而不是 vitality_after；
- Paddle 恢复 Vitality 时不会把 Velocity 重建为固定速度；
- 所有响应之后都满足 `velocity.length() <= max_speed`；
- Ground 反复耗散最终进入 RESTING；
- Wake 分别设置启动 Velocity 与 Vitality；
- 事件在完整结算后发送。

### BallVisuals

- 相同 Velocity 下，改变 Vitality 不改变 Trail capacity；
- 相同 Vitality 下，改变 Velocity 会改变 Trail；
- Glow 接收 Vitality；
- RESTING/零 Velocity 清除 Trail；
- 现有碰撞与 Wake 临时反馈仍可恢复。

不测试：

- Glow 是否美观；
- Trail 是否舒服；
- 休眠节奏是否主观自然；
- Paddle 是否主观具有“重新注入运动”的感觉。

这些留给人工试玩。

## 15. 验收标准

机器验收：

- 工程与所有脚本可解析；
- 新旧模型迁移后不存在运行时 BallEnergyModel 引用；
- Vitality 与 Velocity 可分别设置和演化；
- SurfaceResponseModel 对相同输入返回相同结果；
- 碰撞结算遵守“Velocity first, Vitality second”；
- Paddle impulse 固定且受最大速度限制；
- Ground 重复耗散能够进入 RESTING；
- Trail 不再读取 Vitality；
- Glow 不再读取 Velocity；
- Combo、Timer、Wake 手势和 Endless 主循环无回归；
- headless 测试、主场景 smoke 和持续帧运行通过。

人工试玩观察：

1. Velocity 与 Vitality 分离后运动是否更自然；
2. Ground 是否形成小跳/滚动后休眠；
3. Paddle 是否有重新注入运动的感觉；
4. Trail 与 Glow 是否清楚表达不同信息；
5. 是否出现无限加速、空中冻结或接球减速。

完成机器验证后停止在人工试玩门，不继续主题、音效或玩法扩展。

## 16. 风险与控制

| 风险 | 控制 |
|---|---|
| Ground 低速接触每帧重复结算，导致过快休眠 | 用确定性持续帧测试观察碰撞次数；必要时只调整集中参数或接触去重，不新增玩法状态 |
| Ground 水平速度衰减不足，长期滚动不能 Rest | 使用 tangent retention 与 total-speed settle 门槛共同验证 |
| Paddle impulse 叠加后持续撞上 max cap，失去层次 | 初始 impulse 保守设置；测试保证不超限，体验值留给试玩 |
| Event 层演变为全局架构 | V0.1.2 仅使用局部 signals；不创建 singleton 或 Audio 模块 |
| CollisionResult 被下游改写 | Result 按只读快照使用，Controller 在发送事件前完成所有结算 |
| 历史 Energy 文档与当前实现混淆 | 保留历史规格，并在当前入口文档明确 V0.1.2 替代关系 |
