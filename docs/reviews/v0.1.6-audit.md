### Issues

**C1 — P1 Important：Activity 的通知回调仍隐式执行物理停稳。已确认结构问题，未发现由当前正常入口引起的严重运行故障。**

- 位置：[ball_controller.gd](../../scripts/ball/ball_controller.gd) 第 303–307 行 `_on_vitality_state_changed()`，第 289–294 行 `_settle_resting_motion()`。
- 路径：`resolve_activity(true)` → `activity_state_changed` 同步通知 → `_settle_resting_motion()` → Velocity 清零、Rest 计时归零、Wake 采样／消费状态复位。该回调本身不验证碰撞、支撑或 settle 条件；所以“Activity 只负责活跃状态”在控制器层不成立。
- 静态复现条件：配置 Ball，置低 Vitality、给非零速度，然后调用其模型 `resolve_activity(true)`，会由状态回调清零速度。现有测试经常用同类方式构造休息球；`test_ball_controller.gd` 只验证普通 `set_vitality(0.25)` 不重建速度，不能证明 RESTING 转换无物理副作用。
- 当前生产入口在 Ground settle、Paddle 低能停稳或异常地面恢复后调用，因此尚无证据表明正常飞行会无故清零；不要把结构缺口升级成已复现玩法故障。但未来重用状态转换、接入新唤醒／恢复入口时，会隐藏地改写物理结果。Paddle settle 路径还会在回调后再次显式调用停稳 helper，增加维护歧义。
- 建议：后续授权修复时，把停稳速度处理放在经过物理条件验证的明确提交点；Activity 通知只通知状态。保留当前停稳结果、休息延迟及 Wake 重置契约，并先补能区分“状态通知”和“物理停稳”的回归。

**C2 — P2 Improvement：Support 检查与 Interaction 生命周期仍有直接耦合。已确认，行为本身符合 V0.1.5 取消规则。**

- 位置：[ball_controller.gd](../../scripts/ball/ball_controller.gd) 第 340–353 行。支撑查询先要求 RESTING 且近零速度；丢失支撑时直接 `_clear_wake_sample()`，修改交互强度、累计距离、采样时间。碰撞停稳 helper 同时修改物理速度和交互资格。
- 因此 Support 是“休息静止支撑”的记录，不是所有活动状态下的通用接触记录；Physics／Support 直接重置 Interaction 的路径实际存在。`_refresh_support()` 自身没有隐藏的 Velocity 赋值，也没有平台速度继承，应与 C1 区分。
- 支撑丢失清空旧采样有明确契约及回归，不能简单删掉。建议以后将“支撑变化事实”和“取消 Interaction 采样”的决策在控制器内显式衔接；不需要新全局管理器或替代物理系统。

### Risks

**R1 — P2 Improvement：同帧顺序依赖场景树顺序，自动调度覆盖不足。** [main.tscn](../../scenes/main.tscn) 第 91、104 行把 Ball 放在 Paddle 前，两者未显式设置不同物理优先级。[test_physics_scenarios.gd](../../tests/test_physics_scenarios.gd) 禁用两者自动物理处理，再手动调用；有的测试还故意先移动 Paddle 再处理 Ball。它验证许多几何结果和“碰撞后再输入”结果，但不直接锁定真实主循环顺序。重排节点后可能先 Wake 后碰撞，或改变支撑取消／窗口边界。建议补自动调度顺序断言，或显式表达当前顺序；当前未复现重复启动。

**R2 — P2 Improvement：Ball 对外的 `vitality_changed` 不是完整活力变更流。** [ball_controller.gd](../../scripts/ball/ball_controller.gd) 第 11、143–149、218、256 行：控制器仅在普通 Surface 路径主动发该信号，未转发模型的同名信号；Strong Wake 和初始化改活力时不会发控制器信号。目前视觉主动刷新，Rules／音频使用其他信号，因此未发现现有 UI 故障。以后监听者若依赖该名称会漏 Wake。建议明确其语义或统一变更通知，避免重复发碰撞通知。

**R3 — P2 Improvement：成功 Wake 事件不保证每次都有专属声音。** [basic_audio_feedback.gd](../../scripts/audio/basic_audio_feedback.gd) 第 100–114 行：Wake 正确绑定成功提交，但仍受 40 ms 跨事件抑制及自身冷却影响；若紧邻之前的非 Wall 碰撞音，会被拒绝。已确认是通用限密度策略，不是 Wake 接线错误或弱输入发声。现有音频场景在 Wake 前推进 0.2 s，未覆盖紧邻碰撞的成功 Wake。建议后续先补组合证据、人工听感判断，再决定是否需要优先级调整；不自动增加叠音。

**R4 — P3 Future：高速 Paddle 无 sweep 的已知接触覆盖边界。** [paddle_controller.gd](../../scripts/paddle/paddle_controller.gd) `advance_motion()` 直接改位置；没有 swept contact 或相对运动求解。快速横移可能跨过球，当前测试不是全输入速度／相位的完备覆盖。已有 V0.1.5 文档明确登记，不是本轮新增回归，不纳入本轮实现。

**R5 — P2 Improvement：`configure()` 隐含重新开局。** [ball_controller.gd](../../scripts/ball/ball_controller.gd) 第 143–164 行重新创建模型并 `start_active()`；Main 又显式调用 `start_active()`。当前启动可用，F1 直接改 tuning 不调用该入口，故不是当前调参必然重置的问题。若未来把 configure 当作纯配置重用，会重置速度、Vitality、支撑及 Wake；其他生命周期监听者也未必随之重置。建议明确只限初始化或在后续授权维护中拆分配置与开局。

## 2. Design Audit

### Consistent

| 基线检查 | 当前实现 | 结论与边界 |
| --- | --- | --- |
| Physics / Interaction 双层 | 自由运动由 Velocity、固定 Gravity、Collision 和 Surface Response 决定；输入通过标量交互阈值恢复活力，弱输入只几何回应。Trail 数量／间距／透明度读取速度和运动历史，不读活力或活动态来关掉高速残影。 | 主要语义符合。真实碰撞和必要的固定 Wake 启动是基线允许的跨层事件，不应误报为“输入控制运动”。结构分离见 C1、C2；Glow 例外见 D2。 |
| Vitality 有实质作用 | 各表面恢复系数按碰撞前 Vitality 插值；Ground 系数 0.12–0.78，Ground 活力保留 0.65。有效 Paddle 碰撞恢复缺失活力，Strong Wake 加 0.15。 | 活力不是纯视觉数值，能改变后续反弹及持续运动能力；方向由法线和已有速度决定，Vitality 不指定目标方向。 |
| 球的自主性 | 玩家停止输入后仍有重力、碰撞、衰减；Paddle 不承载横移、不把水平速度传给球；Strong 对已在空中运动的 RESTING 球仅恢复活力。Paddle 遮住起跳路径时仍正常下沿反弹。 | 符合“玩家决定是否继续互动，世界决定接下来会发生什么”。固定向上启动是基线明确允许的启动表现，不要求为了未知感增加随机性。 |
| 观察—介入—回应 | 无 Game Over、任务、倒计时失败、排行榜或最高分；可以不介入并观察球停稳，再用简单横向输入回应。 | 核心循环符合；常驻 Combo／计时造成的注意力导向见 D1，不据此声称整体已变成竞技游戏。 |
| 行为证据 | 正常游戏不显示人格、情绪标签或解释球意图的文本。弱几何回应、连续运动、停稳和再次起动提供可观察行为。 | 符合开放投射方向。F1 参数／F2–F6 试听状态是主动打开的开发工具，不等同于人格解释。基线中的“期待”不应被实现成明确人格提示。 |

### Deviations

**D1 — P1 Important：常驻 Combo／TIME 与无分数注意力占用的设计方向存在张力，需明确设计处置。**

- 证据：[endless_rules.gd](../../scripts/rules/endless_rules.gd) `handle_paddle_hit()` 每次接球增加 Combo，Ground 清零；活跃时间逐帧累计、休息暂停、Wake 重置。[prototype_hud.gd](../../scripts/ui/prototype_hud.gd) 常驻显示 `COMBO` 和 `TIME`，场景中保留对应 Label。
- 相对新基线，连续成功计数和持续时间可诱导“保持连击／延长活跃时间”的自发目标；这不是任务系统或胜负系统，但不能直接判为“没有分数导向”。这是实现事实加体验风险推断，本轮没有用户研究证明其必然造成压力。
- 历史契约明确允许这两项，因此不是 V0.1.5 越权新增。建议在宣布设计基线完全一致前，明确其属于允许的观察数据例外，还是需要另行授权弱化／移除。本轮不擅自改 UI。

**D2 — P2 Improvement：Core／Glow 实际映射包含 RESTING 状态覆盖，不是纯 Vitality 函数。**

- 证据：[ball_visuals.gd](../../scripts/ball/ball_visuals.gd) 第 49–64 行：RESTING 强制视觉 Vitality 为 0、Glow peak 固定 0.25。相同 Vitality=0.04 时，DECAYING peak=0.274，RESTING peak=0.25，颜色也有状态覆盖。见已有 `test_ball_visuals.gd` 的 RESTING 固定底光断言。
- 新基线写作 Interaction → Vitality → Glow；当前实现更准确是 Vitality + Activity → Core／Glow。差别在低值区间，且不是由移动、碰撞脉冲或弱输入驱动。
- 这是 V0.1.3 明确冻结并已验收的可读性特例，不是本轮视觉回归。建议明确记录为设计允许的映射例外；若要求严格同值同光，再经授权修订并人工复核，不在本轮直接重设计。

### Missing

**M1 — P2 Improvement：没有独立的随时间 Vitality 衰减。已确认实现缺项，是否属于设计必需项待明确。** 基线提及“碰撞和时间中的维持能力”；当前 Vitality 只通过碰撞、初始化、显式 Wake 及开发／测试调用改变，没有每秒 Vitality 衰减项。Gravity 每步运行，运动会在多次碰撞中随时间逐渐损耗，所以不能推断“没有衰减过程”。当前 V0.1.5 契约明确限定正常玩法由碰撞改变活力；基线也未给出时间衰减公式。建议确认该措辞是描述行为经过时间演化，还是新增独立机制的意图。本轮不添加持续衰减。

**M2 — P2 Improvement：本轮缺少针对新基线差异的人工体验判断。** V0.1.5 总体体验历史验收保留；本轮机器测试不能替代对 Combo／TIME 注意力影响、低活力 Glow 状态差别、碰撞邻近 Wake 声可辨识度的判断。上述事项尚未形成新的验收证据，不能写成已通过。

基线提及的未来环境介入不是当前必须实现项；没有随机事件、人格系统或环境机制不构成本轮缺陷，不据此扩大 V0.1.6。

### Should Consider

- **P2 Improvement — C2、R1：** 显式表达支撑丢失到交互取消的边界，补真实调度与采样窗口边界的回归；保留现有 30 / 60 / 120 Hz 场景。
